# Reference set

The hand-labelled ground truth for retrieval evaluation: 50 queries and 1,064
relevance judgements, every one made by a person against the fixed policy in
`docs/LABELLING.md`.

This directory is committed because the data is not derived. Embeddings, chunks,
and indexes can be regenerated by running code; these judgements cannot. They
are the most expensive artifact in the project and the evidence behind every
retrieval figure it reports.

---

## Files

| File | Purpose |
|---|---|
| `reference_set.sql` | `pg_dump --data-only` of `queries` and `judgements`. The restore path. |
| `reference_set.json` | The same data, sorted and pretty-printed, with a counts manifest. The readable, diffable record. |

Both are kept because they do different jobs. The SQL restores exactly,
including the `queries_id_seq` value so query ids survive. The JSON is stable
under sorting, so a change to any single grade shows up as a one-line diff in
`git log -p` — which is what makes the labelling history auditable rather than
merely asserted.

## What is in it

```
queries:    50     25 harvested (ids 2–26), 25 authored (ids 27–51)
judgements: 1064   16–25 per query
grades:     0=704 (66.2%)   1=208 (19.5%)   2=152 (14.3%)
```

Candidates were pooled from three retrievers — vector search over `bge-m3`
embeddings (k=10), PostgreSQL full-text search (k=10), and a random sample
(k=5) — then de-duplicated and presented in an order derived from a hash of the
query and chunk id, never in any retriever's ranking.

**Harvested** queries are taken verbatim from the corpus's own concept-check
cells, so they share its vocabulary. **Authored** queries were written
separately, asking the same material about itself in different words.

| | queries | judgements | 0 | 1 | 2 | fully-relevant chunks per query |
|---|---|---|---|---|---|---|
| Harvested | 25 | 533 | 63.2% | 17.4% | 19.3% | 4.1 |
| Authored | 25 | 531 | 69.1% | 21.7% | 9.2% | 2.0 |

The gap is structural. Each concept-check question is answered by a dedicated
instructor-answer cell that serves five to eight questions at once, so relevance
is spread thick. An independently phrased question is usually answered in one or
two places. The authored half therefore carries a sparser relevance signal and
is the stricter test of ranking.

**Queries 41, 45 and 51 have no fully-relevant chunk at all.** Each asks why the
material does one thing rather than another, in a case where it does the thing
without ever explaining why — leaving the implementation as the best available
evidence, which the policy grades a 1. They are kept: a query the corpus cannot
fully answer is real information about the corpus. Any metric computed over this
set has to say how those three are treated.

## The corpus dependency

Judgements reference chunks by `(doc_id, ordinal)`, not by content. The chunk
text is **not** in this export, so nothing here republishes third-party
material — which is also why `corpus/` itself is untracked.

The consequence is that a clone can read the labels but cannot rerun retrieval
without the same source notebooks:

| `doc_id` | notebook | chunks |
|---|---|---|
| `0ed93313f216978b` | `Retrival_Ext_QnA_Complete.ipynb` | 310 |
| `38209c124d221c11` | `Generative_RAG.ipynb` | 263 |
| `8665cdee5bd3aba6` | `Bert_QnA_Complete.ipynb` | 352 |

`doc_id` is a hash of file content, so ingesting the same notebooks reproduces
the same ids and ordinals, and these judgements attach correctly. Different
material produces different ids and the judgements will not match — the
`orphaned_judgements` view reports exactly that case.

## Restoring

Into an empty database with the migrations applied:

```bash
createdb -p 5434 -h /tmp daedalus
psql -p 5434 -h /tmp -d daedalus -c "CREATE EXTENSION vector;"
psql -p 5434 -h /tmp -d daedalus --single-transaction -v ON_ERROR_STOP=1 -f migrations/001_initial.sql
psql -p 5434 -h /tmp -d daedalus --single-transaction -v ON_ERROR_STOP=1 -f migrations/002_reference_set.sql
psql -p 5434 -h /tmp -d daedalus -v ON_ERROR_STOP=1 -f reference-set/reference_set.sql
```

The restore was verified rather than assumed: loaded into a throwaway database
and compared against the live one with an md5 over every query and judgement.
Both sides produced `97592f650ab368f4ec55688b7d521e10`.

## Regenerating

```bash
pg_dump -p 5434 -h /tmp -d daedalus --data-only --table=queries --table=judgements \
  > reference-set/reference_set.sql
```

Two lines of churn are expected even when no data has changed: `pg_dump` writes
a fresh random `\restrict` token on each run, and the JSON carries a
`generated_at` timestamp. A diff touching only those means nothing moved.

**The database is canonical while labelling is in progress; this export is
canonical for anything published.** Labelling is complete, so the export is
effectively frozen — but re-export after any change, or the repository will
report numbers the data no longer supports.

## Provenance

The set is not 1,064 judgements entered cleanly in one pass, and it would be
dishonest to present it that way. Every departure is recorded here.

| Queries | What happened |
|---|---|
| 6 | A misgrade the annotator caught and reconsidered. Regraded. |
| 17, 18, 20 | Buffered keyboard input produced judgements no person made — query 18 took 10 within 2.7 ms. Regraded. |
| 27 | An audit after labelling found the one chunk that answered the query graded 0, at presentation position 16 of 19. Regraded 16/3/0 → 15/3/1. |
| 39 | Annotator-initiated regrade. It also recovered 7 candidates that a silent-skip defect had passed over, taking the query from 18 judgements to its full pool of 25. |
| 49, 50 | 12 judgements written by a text paste into a live session — 11 of them inside 2.2 ms. **Deleted**, not regraded, because no human judgement was ever made. Both queries were then labelled normally. |
| 48 | One mis-keyed grade on `38209c124d221c11:17` corrected by direct SQL update from 1 to 0. This is the only judgement in the set not entered through the labelling tool. |

The defect behind the query 39 shortfall — an unrecognised keypress advancing
silently, indistinguishable from a deliberate skip — was fixed before the last
ten queries were labelled. No judgement recorded after that fix has a gap under
two seconds.

Across the whole set, 16 of 1,064 judgements follow the previous one by under
two seconds, the fastest at 0.87 s. All are isolated, and all predate the fix.
